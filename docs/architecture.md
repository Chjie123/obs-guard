# 架构说明

本文描述 obs-guard 的运行时结构、数据流与关键设计取舍。面向需要修改或扩展本项目的开发者。

---

## 1. 设计目标与约束

| 目标 | 约束条件 |
|---|---|
| 不打断直播 | 渲染线程不得因推理而阻塞；任何异常路径都必须退化为可用状态 |
| 遮挡与画面同帧 | 遮罩必须与产生它的画面在同一帧、同一坐标系内合成 |
| 低延迟 | 从画面出现目标到遮罩生效，附加延迟控制在百毫秒量级 |
| 可替换检测器 | 检测框架与插件主体解耦，便于更换模型或推理后端 |

OBS 的脚本接口（obs-scripting）只能操作既有对象，无法注册新的源类型，也无法调用图形接口。因此渲染链路必须由原生插件实现，脚本仅适用于配置、挂载向导等控制面功能。

---

## 2. 运行时结构

插件运行在 OBS 进程内，包含两个执行体：

```
OBS 渲染线程                                    推理线程
─────────────────────────────────────────────  ────────────────────────────
video_render()
  ├─ 到达检测节拍？
  │    ├─ texrender 渲染输入源
  │    ├─ stage 到 staging surface
  │    ├─ 回读 ROI 并缩放 / letterbox
  │    └─ 投递 FrameView ──────────────────▶ 单槽邮箱（覆盖旧帧）
  │                                              │
  │                                          ONNX Runtime 推理
  │                                              │
  │                                          解码 + NMS + 类别过滤
  │                                              │
  │                                          跟踪与状态机
  │                                              │
  │◀──────────── try_lock 取 MaskFrame ──────────┘
  ├─ 取不到则沿用上一帧结果
  └─ process_filter_begin → 设置 uniform → end
```

### 2.1 线程职责

| 线程 | 职责 | 时间预算 |
|---|---|---|
| 渲染线程 | 节拍控制、取帧、结果获取、遮罩合成 | 每帧 ≤ 2 ms |
| 推理线程 | 推理、后处理、跟踪、结果发布 | 由模型与设备决定 |

渲染线程访问共享结果的唯一方式是 `try_lock`，失败即使用上一帧，不产生任何等待。帧投递采用单槽邮箱：推理慢于取帧时，新帧覆盖旧帧，延迟不累积。

### 2.2 配置的跨线程传递

配置由 UI 线程写入、渲染线程读取，其中包含 `std::string`。直接共享结构体会产生撕裂读取，因此配置以 `std::shared_ptr<const Config>` 承载，通过 `std::atomic_load` / `std::atomic_store` 原子替换。

## 3. 数据流

一帧数据依次经过以下形态：

| 阶段 | 数据结构 | 坐标系 |
|---|---|---|
| 取帧 | `FrameView` | 模型输入像素（已 letterbox） |
| 检测 | `Detection` | 检测区域归一化 0–1 |
| 跟踪 | `MaskCmd` | 整帧归一化 0–1 |
| 合成 | uniform | 整帧 UV 0–1 |

四段坐标的换算必须完全一致，否则表现为遮罩整体偏移或尺寸不符：

1. **模型空间 → 内容空间**：扣除 letterbox 填充比例。
2. **内容空间 → 检测区域空间**：除以内容区尺寸。
3. **检测区域空间 → 整帧空间**：`frame = roi.origin + local * roi.size`。

检测区域的像素值在每次绘制前由当前帧尺寸实时计算，因此分辨率变化或切换坐标系时无需重置内部状态。

## 4. 模块职责

| 目录 | 职责 | 关键点 |
|---|---|---|
| `src/filter/` | 滤镜实体与属性面板 | `filter.cpp` 持有 OBS 上下文；`properties.cpp` 只构建界面，不参与渲染 |
| `src/core/` | 数据契约、常量、配置、推理线程、跟踪 | `types.h` 是唯一的跨模块契约；`constants.h` 收拢全局数值 |
| `src/capture/` | 检测区域取帧与缩放 | 唯一进行 GPU 回读的位置 |
| `src/detect/` | 推理会话与输出后处理 | `detector_ort.cpp` 只管会话与张量；`yolo_post.cpp` 负责解码、NMS、坐标回映射，可脱离推理框架单独验证 |
| `src/render/` | 遮罩合成 | 唯一持有着色器与 uniform 的位置 |

模块之间只通过 `src/core/types.h` 中的结构体通信，不做跨模块直接调用。属性面板与后处理之所以独立成文件，是因为二者变更频率最高，且都不应牵动渲染路径。

## 5. 关键设计取舍

### 5.1 遮罩合成采用单 pass

一帧最多 16 个遮罩矩形。实现方式是在像素着色器中展开 16 段判定，而非逐矩形发起 draw call，也未使用着色器数组与动态索引——后者在不同后端与着色器编译路径上存在兼容性差异。

代价是 uniform 数量较多（16 组矩形 + 16 个不透明度系数），收益是渲染开销与矩形数量无关，且避免了多 pass 带来的状态切换。

### 5.2 取帧使用 CPU 回读

当前实现将输入源渲染至 texrender，整帧 stage 到 staging surface 后回读，再在 CPU 完成区域裁剪与缩放。

这一路径不绑定渲染后端（D3D11 / OpenGL 均可运行），实现简单、失败面小。代价是 1080p 下单次回读约 3–5 ms，且会产生一次 GPU 同步点。

零拷贝方案（共享纹理 + Keyed Mutex）可将该开销降至 1 ms 以内，但需要针对 D3D11 后端特化。这是当前版本已知的主要性能债，替换范围限定在 `src/capture/`。

### 5.3 遮挡只增不减

目标被确认后，遮罩不会因为单帧漏检而立即撤销，而是进入保持期再淡出。原因是漏检几乎必然发生，若遮罩跟随单帧结果跳动，观众会看到持续闪烁，且每一次闪烁都是一次内容泄漏。

同一机制也用于抑制检测间隔造成的闪烁：检测 10 fps，绘制逐帧进行，中间帧沿用上一帧的框体。

### 5.4 疑似目标即刻遮挡

置信度介于低阈值与确认阈值之间的目标，以较低不透明度立即遮挡，而非等待连续命中确认。误遮的体验代价远低于漏遮的合规代价，这一取舍在实现上体现为两档不透明度而非两套流程。

## 6. 失败与降级

推理进程不可用、模型加载失败或推理超时时，按配置执行：

| 策略 | 行为 | 适用 |
|---|---|---|
| `fail-open` | 停止遮挡，画面直通，日志告警 | 一般直播间，优先保证直播可用 |
| `fail-closed` | 全屏遮挡直至恢复 | 高风险直播间，优先保证合规 |

`fail-closed` 设有 3 秒启动宽限期，避免 OBS 启动瞬间模型尚未加载完成时出现全屏黑屏。
